# Requirements Document

## Introduction

The User Management module is a critical system feature for Define Horizon Business Management System that enables administrators to provision, manage, and control user accounts and their access to the system. Built on the existing Supabase authentication foundation, this module extends authentication capabilities to provide comprehensive user lifecycle management, role-based access control (RBAC), departmental organization, and audit tracking for a Zimbabwe-based IT company operating across multiple branches. The User Management module ensures that access control is enforced consistently, users are assigned appropriate roles and responsibilities, and all user-related actions are tracked for compliance and security purposes.

## Glossary

- **User**: An employee or agent of Define Horizon with a System account and assigned Role and Branch
- **System**: Define Horizon Business Management System (DH-BMS) User Management Module
- **Role**: A named set of permissions determining what actions a User can perform (Admin, Manager, Staff, Viewer)
- **Permission**: A specific capability granted to a Role (e.g., create_user, view_users, manage_roles)
- **Admin**: User with Super Administrator Role having unrestricted system access (equivalent to Super Administrator in main system)
- **Manager**: User with Manager Role having authority within assigned Branch (equivalent to Branch Manager)
- **Staff**: User with Staff Role having operational capabilities (equivalent to Employee/Agent)
- **Viewer**: User with Viewer Role having read-only access (equivalent to Auditor)
- **Branch**: A physical or logical division of Define Horizon's operations
- **Department**: A functional division within a Branch (e.g., Sales, Technical Support, Finance)
- **Status**: User account status indicating whether the account is Active or Inactive
- **RBAC**: Role-Based Access Control system for authorization
- **Password_Hash**: One-way encrypted form of a User's password stored in the System
- **Session**: An authenticated connection between a User and the System
- **Audit_Log**: A record of user management actions (creation, modification, deletion, status changes)
- **User_Profile**: Complete record of a User including name, email, phone, role, branch, department, and metadata
- **Invite_Link**: Secure, time-limited URL sent to new Users for account activation
- **Last_Activity_Timestamp**: Most recent date and time a User performed an action in the System
- **Login_History**: Record of User authentication events with timestamps and IP addresses
- **Bulk_Operation**: A single action affecting multiple Users simultaneously (e.g., bulk role assignment)
- **Search_Filter**: Criteria applied to narrow User list (by name, email, role, branch, status, department)
- **Force_Password_Change**: Flag indicating User must change password on next login
- **Suspend_Reason**: Documented reason for suspending a User account (e.g., "Leave of Absence", "Termination Pending")

## Requirements

### Requirement 1: User Registration and Account Creation

**User Story:** As a System Administrator, I want to create user accounts with validated information, so that I can provision access for new team members quickly and securely.

#### Acceptance Criteria

1. WHEN an Admin accesses the User Management module and initiates user creation, THE System SHALL display a form collecting required fields: Full_Name, Email_Address, Phone_Number, Assigned_Role, Assigned_Branch, Assigned_Department, and Initial_Status.
2. WHEN the User creation form is displayed, THE System SHALL pre-populate Initial_Status with "Active" by default and allow Admin to change to "Inactive" if needed.
3. WHEN Admin submits the user creation form, THE System SHALL validate that Email_Address is unique across all Users in the System; IF Email_Address already exists, THE System SHALL display error message "Email already registered" and reject the form submission.
4. WHEN the form is validated successfully, THE System SHALL validate that all required fields contain appropriate data: Full_Name must be non-empty, Email_Address must match email format pattern, Phone_Number must contain only digits and standard phone separators, Assigned_Role must match a defined Role (Admin, Manager, Staff, Viewer), Assigned_Branch and Assigned_Department must exist in the System.
5. WHEN validation passes, THE System SHALL create a new User record with unique User_ID generated by the System.
6. WHEN a User is created, THE System SHALL immediately send an invitation email to the provided Email_Address containing: secure invitation link valid for 7 days, temporary password (12 characters, auto-generated), and instructions for account setup.
7. WHEN the User receives the invitation email, THE System SHALL log the invitation event in the Audit_Log with timestamp, Admin who invited, and invited email address.
8. WHEN a User clicks the invitation link, THE System SHALL validate the link is not expired (must be within 7 days of creation); IF expired, THE System SHALL display message "Invitation link expired" and offer to request a new invitation.

### Requirement 2: User Password Management

**User Story:** As an Admin or User, I want to securely manage passwords including setting, resetting, and forcing changes, so that account security is maintained.

#### Acceptance Criteria

1. WHEN a new User clicks the invitation link, THE System SHALL display a password setup form requiring: New_Password (minimum 8 characters) and Password_Confirmation.
2. WHEN Password is entered, THE System SHALL validate in real-time that password meets complexity requirements: contains uppercase letter, contains lowercase letter, contains digit, contains special character from set [!@#$%^&*].
3. IF password fails validation, THE System SHALL display specific error message indicating which requirements are not met (e.g., "Missing uppercase letter").
4. WHEN User sets password successfully, THE System SHALL hash the password using bcrypt with minimum cost of 10 and store in Supabase Auth; THE System SHALL NOT store plaintext password.
5. WHEN Admin initiates password reset for an existing User, THE System SHALL generate a secure reset token, send reset email containing time-limited link (valid 24 hours), and log the reset request in Audit_Log.
6. WHEN User clicks password reset link, THE System SHALL validate link validity and display new password form.
7. WHEN User completes password reset, THE System SHALL update password in Supabase Auth and log the reset completion in Audit_Log.
8. WHEN Admin sets Force_Password_Change flag on a User account, THE System SHALL add notification to User's next login indicating password change is required; on next login, THE System SHALL redirect User to password change form before allowing system access.
9. WHEN User changes their own password, THE System SHALL require verification of current password before accepting new password.
10. WHEN password is changed, THE System SHALL invalidate all existing sessions for that User, requiring re-authentication.

### Requirement 3: Role-Based Access Control - Role Definition and Assignment

**User Story:** As a System Administrator, I want to define roles with specific permissions and assign roles to users, so that access is controlled according to job responsibility.

#### Acceptance Criteria

1. THE System SHALL support four predefined Roles: Admin, Manager, Staff, Viewer.
2. WHEN Admin accesses Role Management section, THE System SHALL display all Roles with their descriptions and associated Permissions.
3. THE Admin Role SHALL include the following Permissions: create_user, read_user, update_user, delete_user, manage_roles, manage_permissions, view_audit_log, manage_system_settings, bulk_actions, export_users.
4. THE Manager Role SHALL include Permissions: read_user (Branch-scoped), update_user (Branch-scoped), create_user (Branch-scoped), deactivate_user (Branch-scoped), view_subordinate_activity, view_branch_data, export_branch_users.
5. THE Staff Role SHALL include Permissions: read_user_profile (self and directory), update_user_profile (self only), view_colleagues_profile (directory access), view_personal_activity.
6. THE Viewer Role SHALL include Permissions: read_user (read-only), read_audit_log (read-only), view_reports (read-only).
7. WHEN Admin assigns a Role to a User, THE System SHALL immediately apply the Role's Permissions to that User; changes take effect on User's next login or session refresh.
8. WHEN Admin changes a User's Role, THE System SHALL record the previous Role and change timestamp in the Audit_Log; IF previous Role had higher privileges, THE System SHALL invalidate any existing sessions for that User to force re-authentication with new permissions.
9. WHERE a User's Role is Admin, THE System SHALL display a "system permissions" indicator in User profile view distinguishing Admins from other Roles.

### Requirement 4: Branch and Department Assignment

**User Story:** As a System Administrator or Branch Manager, I want to assign users to specific branches and departments, so that data access is properly scoped and organizational hierarchy is maintained.

#### Acceptance Criteria

1. WHEN a User is created or edited, THE System SHALL require assignment to exactly one Branch and optionally to one Department within that Branch.
2. WHEN Admin creates a User, THE System SHALL validate that the selected Department (if any) belongs to the selected Branch; IF Department belongs to different Branch, THE System SHALL display error and prevent assignment.
3. WHEN a User is assigned to a Branch, THE System SHALL apply Branch-level access control: User can only view and create records associated with their assigned Branch unless User has Admin Role.
4. WHEN User is assigned to a Department, THE System SHALL enable Department-level filtering in reports and data views: Users can see colleagues in same Department and Department-specific activity.
5. WHEN Admin reassigns a User to a different Branch, THE System SHALL update their data access scope immediately; on next login, User will only see data for new Branch.
6. WHEN a Manager views Users in their Branch, THE System SHALL display Users grouped by Department (if applicable) with Department name and member count.
7. WHEN creating a Department, THE System SHALL collect: Department_Name, Parent_Branch, Department_Description, and Manager_Assignment; THE System SHALL assign unique Department_ID.
8. WHERE a User's Role is Manager, THE System SHALL restrict Department management capabilities to their assigned Branch only.

### Requirement 5: User Status Management - Active and Inactive

**User Story:** As a System Administrator or Branch Manager, I want to control user account status to enable and disable access, so that I can manage personnel changes and access control.

#### Acceptance Criteria

1. WHEN Admin views a User profile, THE System SHALL display current Status (Active or Inactive) as editable field with toggle switch.
2. WHEN Admin sets Status to "Active", THE System SHALL immediately enable that User's login capability.
3. WHEN Admin sets Status to "Inactive", THE System SHALL prevent that User from logging in on next authentication attempt; IF User is currently logged in, THE System SHALL terminate their session immediately.
4. WHEN Admin attempts to set Status to "Inactive", THE System SHALL display confirmation dialog requiring Admin to provide Suspension_Reason from predefined list (On Leave, Termination Pending, Performance Review, Security Hold, Other) or free-text reason.
5. WHEN a User is set to "Inactive", THE System SHALL record in Audit_Log: timestamp, Admin who made change, previous status, reason for suspension, and current status.
6. WHEN an "Inactive" User attempts to log in, THE System SHALL reject login and display message "Your account has been suspended. Contact your administrator for details."
7. WHEN Admin reactivates an Inactive User (Status → Active), THE System SHALL restore full access and log reactivation in Audit_Log with timestamp and Admin username.
8. WHERE a User's Role is Manager, THE System SHALL restrict status changes to Users within their assigned Branch only.
9. WHEN Status is changed, THE System SHALL send notification email to affected User explaining status change, reason (if provided), and next steps.

### Requirement 6: User Search and Filtering

**User Story:** As a Manager or Admin, I want to search and filter users by various criteria, so that I can quickly find users and manage groups efficiently.

#### Acceptance Criteria

1. WHEN Admin accesses the User List page, THE System SHALL display a search bar and filter panel.
2. WHEN Admin enters text in search bar, THE System SHALL search across User_Full_Name and Email_Address in real-time and update results as User types.
3. WHEN Admin uses search, THE System SHALL display results with highlighting showing which field matched the search term.
4. WHEN Admin clicks "Advanced Filters" panel, THE System SHALL display filter options: Role (multi-select checkbox), Branch (single-select dropdown), Department (single-select dropdown), Status (Active/Inactive/All), and Date_Range_Created (from/to date picker).
5. WHEN Admin applies filters, THE System SHALL combine filters with AND logic (e.g., Role=Staff AND Branch=Harare AND Status=Active) and update result set.
6. WHEN Admin combines search text with filters, THE System SHALL apply search term first, then filter results; search within Filter_Results.
7. WHEN filter results exceed 100 records, THE System SHALL display pagination with page size options (25, 50, 100, 250 results per page) and current page indicator.
8. WHEN Admin clicks "Clear Filters", THE System SHALL reset search bar and all filter selections, displaying full User list.
9. WHEN Admin saves a filter combination, THE System SHALL store as "Saved Search" with user-provided name (e.g., "Harare Staff Users") and timestamp.
10. WHEN Admin clicks saved search, THE System SHALL apply all saved filter and search criteria with single click.

### Requirement 7: User Profile and Directory

**User Story:** As a Staff or Manager, I want to view user profiles and access a company directory, so that I can find colleague information and understand organizational structure.

#### Acceptance Criteria

1. WHEN any authenticated User accesses the User Directory, THE System SHALL display a searchable list of Users with Name, Title/Role, Department, Branch, and Phone_Number (if visible per permissions).
2. WHEN a User clicks another User's name in directory, THE System SHALL display that User's profile containing: Full_Name, Job_Title, Department, Branch, Phone_Number, Email_Address (optional based on Role), Profile_Picture, and Start_Date.
3. WHEN Staff views a colleague's profile, THE System SHALL display only Name, Department, Branch, Phone, and Profile_Picture; Email_Address SHALL NOT be displayed to Staff.
4. WHEN Manager views a Staff User's profile, THE System SHALL display full profile including Email_Address.
5. WHEN Admin views any User's profile, THE System SHALL display complete profile plus metadata: User_ID, Status, Role, Assigned_Permissions, Last_Activity_Timestamp, Login_Count, Date_Created, Last_Modified.
6. WHEN User updates their own profile, THE System SHALL allow editing: Profile_Picture (avatar/photo upload), Phone_Number (optional), and Display_Preferences (e.g., visibility in directory).
7. WHEN User updates their phone number, THE System SHALL validate format (must match Zimbabwe phone patterns or international format) and log change in Audit_Log.
8. WHEN User uploads Profile_Picture, THE System SHALL validate image format (JPEG, PNG, WebP), resize to 256x256px, and store in secure storage.

### Requirement 8: User Activity Tracking

**User Story:** As a Manager or Admin, I want to monitor user activity including login history and last activity timestamps, so that I can assess user engagement and detect unusual patterns.

#### Acceptance Criteria

1. WHEN a User successfully logs in, THE System SHALL record Login_Event with: User_ID, Login_Timestamp, IP_Address, Browser/Device_Type, and Session_ID.
2. WHEN a User logs out, THE System SHALL record Logout_Timestamp and maintain the Login_Event record.
3. WHEN a User session expires or is terminated, THE System SHALL record Logout_Timestamp as system-initiated.
4. WHENEVER a User performs any action in the System (view page, create/update/delete record), THE System SHALL update Last_Activity_Timestamp for that User.
5. WHEN Admin views a User's activity dashboard, THE System SHALL display: Total_Login_Count, Last_Login_Date/Time, Current_Session_Status (Logged In / Logged Out), and Last_Activity_Timestamp.
6. WHEN Admin accesses "Login History" for a specific User, THE System SHALL display paginated list of recent logins (last 90 days by default) with: Login_Timestamp, Logout_Timestamp, Session_Duration, IP_Address, Device_Type, and Location (if available).
7. WHEN Admin views Login_History, THE System SHALL filter to show only successful logins by default; Admin can toggle to show Failed_Login_Attempts with failure reason (Invalid Credentials, Account Inactive, etc.).
8. WHEN a User remains inactive for 30 minutes, THE System SHALL automatically terminate their session and require re-authentication on next access.
9. WHEN session terminates due to inactivity, THE System SHALL display message "Session expired due to inactivity" and redirect to login page.
10. ALL Login_Events, Logout_Events, and Failed_Login_Attempts SHALL be logged in Audit_Log for compliance tracking.

### Requirement 9: Activity Audit Trail

**User Story:** As an Auditor or Compliance Officer, I want to access comprehensive audit logs of all user management actions, so that I can verify compliance and investigate issues.

#### Acceptance Criteria

1. THE System SHALL log all User Management actions in Audit_Log table with: Action_Type, User_ID_Affected, Admin_User_ID (who performed action), Timestamp, Before_State (previous values), After_State (new values), and Description.
2. THE Audit_Log SHALL record the following Action_Types: user_created, user_updated, user_deleted, user_status_changed, role_assigned, role_revoked, permission_granted, permission_revoked, password_reset, password_changed, login_successful, login_failed, logout, session_terminated, suspension_reason_updated.
3. WHEN a User is created, THE System SHALL log: new User_ID, Full_Name, Email, Role, Branch, Department, assigned by Admin_User_ID, and timestamp.
4. WHEN a User is modified, THE System SHALL log: User_ID, which fields were changed (e.g., Role: Admin → Manager), previous values, new values, modified_by Admin_User_ID, and timestamp.
5. WHEN Admin performs bulk action, THE System SHALL create individual Audit_Log entry for each affected User showing original state and new state.
6. WHEN Viewer accesses Audit_Log, THE System SHALL display all user management entries; WHEN non-Auditor User accesses Audit_Log, THE System SHALL restrict to showing only their own actions.
7. WHEN Admin accesses Audit_Log page, THE System SHALL display filters: Date_Range, Action_Type (multi-select), User_Affected (search/dropdown), and Admin_Performer (search/dropdown).
8. WHEN Audit_Log query would return more than 100,000 entries, THE System SHALL display pagination and offer background export to CSV/Excel with email notification.
9. THE System SHALL retain all Audit_Log entries for minimum 7 years for compliance; deletion of User_Records SHALL NOT delete corresponding Audit_Log entries.

### Requirement 10: Bulk User Operations

**User Story:** As a System Administrator, I want to perform bulk operations on multiple users simultaneously, so that I can manage large groups efficiently without individual updates.

#### Acceptance Criteria

1. WHEN Admin displays User List, THE System SHALL provide checkbox selection for individual Users and "Select All" checkbox for current filtered view.
2. WHEN Admin selects multiple Users and clicks "Bulk Actions" button, THE System SHALL display dropdown menu with available bulk operations: Assign Role, Assign Branch, Assign Department, Change Status (Activate/Deactivate), Reset Password, Force_Password_Change, Export Selected, Delete Selected.
3. WHEN Admin selects "Assign Role" bulk action, THE System SHALL display confirmation dialog showing number of Users affected, current Roles of selected Users, and Role to assign; Admin enters confirmation text to proceed.
4. WHEN "Assign Role" is executed, THE System SHALL update Role for all selected Users, invalidate their sessions to force re-authentication with new permissions, send notification emails to affected Users, and create individual Audit_Log entries.
5. WHEN Admin selects "Change Status" bulk action, THE System SHALL allow selecting target status (Active or Inactive) and Suspension_Reason (required if setting to Inactive).
6. WHEN bulk status change is executed, THE System SHALL update all selected Users, terminate active sessions for Users being deactivated, send email notifications, and log each change individually in Audit_Log.
7. WHEN Admin selects "Export Selected" bulk action, THE System SHALL generate CSV file containing selected Users with columns: User_ID, Full_Name, Email, Role, Branch, Department, Status, Last_Activity, Date_Created.
8. WHEN Admin selects "Delete Selected" bulk action, THE System SHALL display warning showing number of Users to be deleted, require Admin to type username as confirmation, and require email confirmation for execution.
9. WHEN bulk operation completes, THE System SHALL display summary: number of Users updated, success status for each User, and timestamp of operation.

### Requirement 11: User Export and Reporting

**User Story:** As a Manager or Admin, I want to export user lists and generate reports, so that I can share user information and analyze team composition.

#### Acceptance Criteria

1. WHEN Admin clicks "Export Users" button on User List page, THE System SHALL display export format options: CSV, Excel (XLSX), PDF.
2. WHEN Admin selects export format, THE System SHALL gather current Filter_Criteria (if any) and offer options: Export All Users, Export Filtered Results, Export Selected Users.
3. WHEN export is initiated, THE System SHALL compile user data with columns: User_ID, Full_Name, Email_Address, Phone_Number, Assigned_Role, Assigned_Branch, Assigned_Department, Status, Date_Created, Last_Activity_Date.
4. IF export includes Admin-only fields, THE System SHALL include additional columns: Last_Login_Date, Login_Count, Invitation_Date, Password_Reset_Date.
5. WHEN CSV export is generated, THE System SHALL properly escape special characters (commas, quotes, newlines), include UTF-8 encoding for Zimbabwe-specific characters if present, and provide immediate download.
6. WHEN PDF export is generated, THE System SHALL include: report title "User Listing Report", export timestamp, Admin who initiated export, applied filters, user count, and professional formatting with headers/footers.
7. WHEN export exceeds 10,000 records, THE System SHALL offer asynchronous processing: generate in background, send download link via email, and display progress indicator.
8. WHEN Admin generates report, THE System SHALL log export action in Audit_Log with: report_type, export_format, record_count, filters_applied, Admin_User_ID, and timestamp.

### Requirement 12: User Deactivation and Suspension

**User Story:** As a System Administrator or Branch Manager, I want to suspend or deactivate user accounts with documented reasons, so that I can manage personnel changes while maintaining audit trails.

#### Acceptance Criteria

1. WHEN Admin initiates user deactivation, THE System SHALL display modal with mandatory fields: Suspension_Reason (dropdown selection or free text), Suspension_Date (defaults to today), and Suspension_Notes (optional detailed explanation).
2. WHEN Suspension_Reason dropdown is shown, THE System SHALL display predefined options: On Leave, Termination Pending, Disciplinary Action, Performance Review, Security Hold, Other.
3. WHEN Admin selects "Other", THE System SHALL reveal text field for free-text Suspension_Reason.
4. WHEN deactivation is confirmed, THE System SHALL: (a) set Status to Inactive, (b) record suspension details, (c) terminate any active sessions, (d) send notification email to User, (e) log action in Audit_Log.
5. WHEN deactivated User is logged in at time of deactivation, THE System SHALL immediately terminate session and on next page interaction display message "Your account has been deactivated."
6. WHEN Admin views a deactivated User's profile, THE System SHALL display: deactivation date, deactivation reason, and option to reactivate.
7. WHEN Admin reactivates a User, THE System SHALL display confirmation dialog showing previous deactivation reason; upon confirmation, THE System SHALL set Status to Active, log reactivation in Audit_Log, and send notification email.
8. WHEN a User is deactivated, THE System SHALL retain all historical records (created records, activity history, audit logs) permanently.
9. WHEN Admin permanently deletes a User account, THE System SHALL display final warning requiring typed confirmation of User email address; only then allow deletion.

### Requirement 13: User Invitation and Onboarding

**User Story:** As a System Administrator, I want to invite new users with automated email communications, so that user onboarding is streamlined and new employees can quickly access the system.

#### Acceptance Criteria

1. WHEN Admin creates a new User account, THE System SHALL automatically generate and send Invitation_Email to provided Email_Address.
2. THE Invitation_Email SHALL contain: greeting with User's name, temporary password (12-character alphanumeric with special character), secure invitation link, link expiration date (7 days), and instructions for account setup.
3. WHEN User receives invitation, THE System SHALL also send separate SMS (if phone number provided) with message "Welcome to Define Horizon! Click: [link] to activate your account. Link expires in 7 days."
4. WHEN User clicks invitation link, THE System SHALL validate link signature and expiration; IF link is valid, redirect to account setup page.
5. WHEN User completes account setup (sets password), THE System SHALL mark invitation as "Accepted", log event in Audit_Log, and send confirmation email.
6. WHEN invitation link expires (7 days), THE System SHALL mark invitation as "Expired" and Admin can resend invitation from User profile.
7. WHEN Admin clicks "Resend Invitation", THE System SHALL generate new invitation link (7-day expiration), send new Invitation_Email, and log resend in Audit_Log.
8. IF User does not accept invitation within 7 days, THE System SHALL display notification to Admin on dashboard showing pending invitations.
9. WHEN User accepts invitation and sets password, THE System SHALL send final Welcome_Email with: login instructions, direct link to system, support contact information, and tip of useful feature.

### Requirement 14: Permission Management

**User Story:** As a System Administrator, I want to define and manage granular permissions assigned to roles, so that I can enforce the principle of least privilege.

#### Acceptance Criteria

1. WHEN Admin accesses Permission Management section, THE System SHALL display all defined Permissions organized by category (User_Management, Data_Management, Reports, Settings, Audit).
2. THE System SHALL support the following Permissions in User_Management category: create_user, read_user, update_user, delete_user, manage_roles, manage_permissions, view_activity_log, manage_branch_assignment.
3. WHEN Admin views a Role, THE System SHALL display all Permissions associated with that Role with checkboxes.
4. WHEN Admin edits Role Permissions, THE System SHALL allow adding/removing individual Permissions; changes display confirmation of how many Users will be affected.
5. WHEN Admin modifies Role Permissions, THE System SHALL apply changes immediately to all Users with that Role; affected Users' active sessions are invalidated to force re-authentication.
6. THE System SHALL prevent Admin from removing all Permissions from a Role; if attempted, THE System SHALL display error "Cannot remove all permissions from a role."
7. WHEN Admin attempts to create custom role (future enhancement), THE System SHALL validate that Role_Name is unique and contains only alphanumeric characters and underscores.
8. WHEN Permission is added to a Role, THE System SHALL log change in Audit_Log with: Role_Name, Permission added, Admin_User_ID, and timestamp.

### Requirement 17: Error Handling and Validation

**User Story:** As a User, I want the system to validate inputs and provide helpful error messages, so that I can correct mistakes easily.

#### Acceptance Criteria

1. WHEN Admin submits User creation form with empty required field, THE System SHALL display inline error message below field indicating field name and requirement (e.g., "Full Name is required").
2. WHEN Admin enters invalid Email_Address, THE System SHALL display error "Please enter a valid email address" with email format example.
3. WHEN Admin enters Phone_Number that fails validation, THE System SHALL display error with accepted format examples for Zimbabwe (+263-71-xxx-xxxx or similar).
4. IF email uniqueness check reveals duplicate email, THE System SHALL display error "Email address already in use. Please use a different email or contact the administrator if this is an error."
5. WHEN password validation fails, THE System SHALL display requirement checklist showing: (✓ or ✗) at least 8 characters, (✓ or ✗) uppercase letter, (✓ or ✗) lowercase letter, (✓ or ✗) digit, (✓ or ✗) special character.
6. WHEN form submission fails due to database error, THE System SHALL display user-friendly message "An error occurred while saving. Please try again or contact support" without exposing technical details.
7. WHEN Admin attempts bulk operation on 0 selected Users, THE System SHALL disable bulk action buttons and display message "Select at least one user to perform bulk actions."
8. WHEN system detects attempted access to User Management by non-Admin User, THE System SHALL log unauthorized access attempt in Audit_Log and display "Access Denied" message.

### Requirement 18: Data Consistency and Concurrency

**User Story:** As a System Administrator, I want data consistency to be maintained even when multiple admins manage users simultaneously, so that user records remain accurate and conflicts are handled appropriately.

#### Acceptance Criteria

1. WHEN two Admins attempt to update the same User simultaneously, THE System SHALL use optimistic locking: first Admin's update succeeds, second Admin receives error "User record was modified by another admin. Please refresh and try again."
2. WHEN User record is being viewed and another Admin modifies it, THE System SHALL display banner at top "User information has been updated by [Admin_Name]. Click to refresh." with refresh button.
3. WHEN Admin clicks refresh button, THE System SHALL reload User_Profile with latest data.
4. WHEN bulk operation modifies User records, THE System SHALL ensure atomicity: if any User update fails, THE System SHALL rollback all changes and report which Users failed and why.
5. WHEN Admin deletes User and another Admin simultaneously tries to modify same User, THE System SHALL return error "User no longer exists" to second Admin.

### Requirement 19: Security - Password and Credentials

**User Story:** As a Security Administrator, I want robust password policies and secure credential handling, so that accounts are protected against unauthorized access.

#### Acceptance Criteria

1. WHEN Admin sets or resets password, THE System SHALL enforce: minimum 8 characters, maximum 128 characters, must contain uppercase, lowercase, digit, and special character.
2. WHEN password is stored, THE System SHALL use Supabase Auth's secure password hashing (bcrypt minimum cost 10); plaintext passwords SHALL NOT be logged or stored anywhere.
3. WHEN User sets password, THE System SHALL not allow reusing previous 5 passwords.
4. WHEN password is set, THE System SHALL log password_change event in Audit_Log without recording password value.
5. WHEN Admin resets User's password, THE System SHALL NOT display password in UI; temporary password is sent only via email.
6. WHEN invitation email with temporary password is sent, THE System SHALL mark password as "temporary" and flag Force_Password_Change; User must change password on first login.
7. WHEN User attempts login with incorrect password more than 5 times within 15 minutes, THE System SHALL temporarily lock account for 15 minutes, send security alert email to User, and log failed attempt in Audit_Log.
8. THE System SHALL implement CSRF protection on all POST/PUT/DELETE endpoints using token-based verification.
9. WHEN Admin performs sensitive operations (reset password, delete user), THE System SHALL require Admin to enter their own password as additional confirmation.

### Requirement 20: System Integration - Supabase Authentication

**User Story:** As a Developer, I want the User Management module to integrate seamlessly with Supabase Auth, so that authentication is reliable and follows security best practices.

#### Acceptance Criteria

1. THE System SHALL use Supabase Auth as the primary authentication provider; all passwords stored and validated through Supabase.
2. WHEN User logs in, THE System SHALL call Supabase Auth endpoint, validate credentials, and receive JWT token.
3. WHEN new User is invited, THE System SHALL create corresponding Supabase Auth user with provided email; password is set during invitation acceptance.
4. WHEN Admin resets password, THE System SHALL call Supabase endpoint to invalidate existing password and trigger reset workflow.
5. WHEN User deletes their account (if allowed), THE System SHALL also delete corresponding Supabase Auth user.
6. WHEN User changes email (if allowed), THE System SHALL update both DH-BMS database and Supabase Auth user email.
7. THE System SHALL implement Row-Level Security (RLS) at Supabase database level: Users can only access their own User_Profile record and subordinate records based on Role and Branch.
8. WHEN accessing Users table, THE System SHALL apply RLS policy: Admin can access all Users, Manager can access Branch users, Staff can access self only.
